# Архитектура

Один процесс на Go, один файл базы, никакой сборки фронтенда. Так проще поддерживать одному человеку и дешевле
держать на маленьком сервере.

```
cmd/joblox        запуск, настройки из окружения, команды serve, check, health, version
internal/profile    профиль бизнеса: чтение YAML и проверка графа статусов
internal/flow       движок статусов: какие переходы открыты, применение перехода
internal/money      суммы в копейках
internal/order      ядро: оформление, цена, антифрод, коды, переходы, действия оператора, правило показа реквизитов
internal/antifraud  правила решения по заказу
internal/store      SQLite: заказы, журнал событий, чёрный список
internal/mail       SMTP и почтовый ящик в памяти для режима разработки
internal/bot        бот операторов в Telegram
internal/web        витрина, страница заказа, защита, дашборд; шаблоны и статика вшиты в бинарник
internal/metrics    Prometheus и живая сводка для дашборда
internal/hub        Joblox Network: сервер счётчика (joblox hub) и отправка чисел из установки
profiles/           готовые профили
k6/                 функциональные сценарии и нагрузка
monitoring/         Prometheus, тревоги с тестами, генератор дашборда Grafana
deploy/             Docker, Caddy, systemd, примеры настроек
```

Зависимости направлены внутрь: `web` и `bot` зовут `order`, `order` зовёт `flow`, `antifraud` и интерфейс
`order.Store`. Ядро не знает про HTTP и Telegram, поэтому его тесты быстрые и точные.

## Заказ

Заказ хранит статус, позиции, ответы клиента, сумму и флаги: оплачен, одобрен, цена известна, email подтверждён.
Статус меняется только переходом профиля. Флаги ставят только действия оператора. Каждая запись заказа
увеличивает версию, а запись сравнивает версию с прочитанной: два одновременных нажатия не перезапишут
друг друга.

## Почему так

- **Отрисовка на сервере вместо SPA.** Формы работают без JavaScript, нет сборки и сотен npm-пакетов, а значит
  меньше уязвимостей в цепочке поставки. Скрипта на страницах около 60 строк: подсказка суммы, обновление
  статуса и счётчик онлайн.
- **SQLite.** Отдельный сервер базы не нужен, резервная копия делается копированием одного файла. Для одного
  бизнеса это с запасом: запись одна за раз, но заказ пишется за доли миллисекунды.
- **Telegram long polling.** Не нужен входящий адрес для бота, работает за NAT.

## Масштабирование

Нагрузочный тест в CI проверяет 60 посетителей в секунду с порогами по времени ответа. Предел своего сервера
измеряйте тем же тестом с большим `RATE`. Если станет мало:

1. Больше ядер у того же сервера: Go использует их сам.
2. Несколько процессов за балансировщиком. Для этого нужна общая база: реализуйте `order.Store` для PostgreSQL,
   интерфейс маленький. Лимиты запросов и счётчик онлайн сейчас живут в памяти процесса, при нескольких
   процессах их нужно вынести в общее хранилище или считать на балансировщике.
3. Бот запускайте в одном процессе: Telegram отдаёт обновления только одному получателю.
